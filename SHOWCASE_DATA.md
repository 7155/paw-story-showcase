# Showcase data contract

Live demonstration state in this repository is synthetic. The data deliberately follows the
same frontend contracts and transport interface as PAWOS, but it never claims
to be a production Session, Room, Memory item, retrieval result, Browser guest,
or Terminal process. Historical Lab results are separately labeled public
receipts, projected from a fixed snapshot rather than generated by a live run.

## Native click-through guide

The primary page and detail routes embed real PAW components. The guide in
`control-center-web/src/paw-os/showcase/hands-on-guide.ts` highlights an
existing control, observes its normal click and checks the rendered outcome.
Automatic playback clicks those same controls, then waits for their rendered result. It never writes Runtime state to fabricate a completed step.
The host validates each progress message against its iframe, origin and
instance. Native window maximization is only a presentation default.

Room file reads preserve the requested Session identity. Memory topic and
source references resolve to the same synthetic input-history records.
`preview-trace-report-routes.ts` persists contract-valid synthetic reports
for the supplied public incident; unknown targets remain unavailable, and
these reports do not claim new model inference, repair or production proof.
A download click is not proof that the browser saved the package.

## Agent Lab public boundary

`/lab` is the dedicated four-scenario demonstration page. EnterpriseOps, RAG,
CloudOps and Memory each open a separate project in the current PAW Lab UI.
Each starts with zero imported materials. The real project UI accepts a sample
or user-provided JSON containing `records` and `cases`, saves a candidate
strategy as a versioned form, and executes the scenario's local deterministic
rules against every imported case. A current, fully passing evaluation allows
an offline App version to be prepared, tried in an opaque isolated preview,
and exported as a ZIP containing `index.html`, data, evaluation and a README.
Changed materials or saved configuration invalidate preparation until a new
evaluation passes. Package generation uses the same rule function and frozen
data that were evaluated; no Provider or private Runtime is involved.

The current-run evaluation is explicitly `offline-rule-evaluation`, not a
model benchmark. RAG checks a local Top-1 source, EnterpriseOps checks sample
business constraints, CloudOps checks sample diagnostic rules, and Memory
checks sample retention rules. Historical Agent candidate matrices still use
`agent-lab-current-20260905.v1.json`, in a separate disclosure. Editing the
project never modifies those historical receipts. The UI opens through the
existing `context-` showcase mode, so the real Lab window starts maximized.

`agent-lab` opens the current PAW project workbench. The public sample contains
two synthetic materials, a task brief and an acceptance table. Visitors can
browse artifacts, keep separate edited revisions, inspect Knowledge sources,
and search only the in-memory sample. These edits last for the current preview
transport; reloading starts a fresh demonstration. No Provider is called, no
machine path is read, and no indexing, evaluation, installation or App build is
reported as executed. The four guided scenarios additionally support the
offline evaluation and packaging described above. Other real execution
commands return an explicit public-preview limitation.

The legacy “已有实验” view retains the four vertical workflows: EnterpriseOps / CI,
Enterprise RAG, CloudOps and Memory Maintenance. Its matrix starts with the human-readable fields
that answer “what was the original data, what counted as correct, what failed,
what changed and what happened afterwards”.  Technical identifiers are kept
behind the detail page's “工程证据” disclosure.

The four rows use different evidence labels and must not be conflated:

| Scenario | Public source label | What the numbers mean |
| --- | --- | --- |
| EnterpriseOps / CI | `deterministic fixture` | Fixed tasks and verifiers projected from source-local receipts; the final Held-out result is retained as a rejected one-shot gate and is not rerun. |
| Enterprise RAG | `public benchmark` | Public-safe document/query and answer-gate summary; retrieval improvement does not imply citation-gate success. |

| Memory Maintenance | `private-shadow human rubric` | Five synthetic/private-shadow cases judged against a human-defined “save four, abstain one” rubric; it is not production user memory. |

Each row can open a detail view showing its candidate timeline, Room roles,
bounded evidence excerpts, before/after metrics, rejected branches and final
decision.  The “审计报告” action creates a self-contained HTML document in
the browser.  It is a rendering of the public fixture, not a hidden transcript
export.  Downloaded reports repeat the source label and the non-production
boundary so they remain safe when shared outside the site.

The `memory-flow` showcase reuses one real PAWOS desktop and five staged App
routes: `/history` → `/memory?view=organize` → `/memory?layer=timelines` →
`/agent?session=session-memory-greeting` → `/agent?session=session-memory`.
Its frozen day contains 1,284 complete-input events, six representative

Memory result remains visible for reading before the Agent window opens. The
conversation then grows from an ordinary “嗨，今天怎么样？” greeting to one

same displayed window. Processing wait is compressed; all visible dwell is
reading time. Each stage waits until its real owning App renders the frozen
result before that reading timer starts, so a cold lazy chunk cannot skip a
visible step. Raw input is not copied into the Agent transcript, and every
Timeline / Atom result keeps a source-reference boundary.

The read-only `session-reliability` fixture and separate writable

must not remount or replace the OS shell.

## Required labels

- `synthetic-preview`: contract-shaped generated state; no real Runtime claim.
- `interaction-rehearsal`: an action updates only in-memory showcase state.
- `host-unavailable`: a native/Electron/PTY capability is intentionally absent.
- `live`: prohibited unless a future public sandbox supplies separate evidence.

The production source, tests, build, installed application, running Runtime,
foreground behavior, and user acceptance are separate evidence levels.

## Expanded world scenarios (September 2026)

`showcase/world.v2.json` is the supplied public synthetic story. Its 6 Agents,
9 tasks, 51 messages, 40 tool calls and 9 hashed artifacts are reference data,
not a private Runtime transcript. Native Room events retain their 69-event
recovery contract, with longer input, memory, collaboration and OS discussions
and readable Markdown contracts. The first chapter restores the original
WebGL planets, then opens the real main and four Partner windows. Pausing or

The Reviewer arrives after implementation; the rollback issue remains open
at this chapter's end.

The native Lab optimization project executes `showcase/optimization.ts` against
eight distinct faults. File contents, revisions, write/registration counts,
receipts and recovery determine the results: baseline 3/8, reduced-step
candidate 4/8, repaired candidate 8/8. Adoption requires a current comparison
under frozen conditions. The displayed token and price estimates are explicitly
synthetic; no new Provider measurement or production fix is claimed.

The four imported Lab datasets are generated from the world by
`python3 scripts/generate-world-lab.py`; `--check` verifies freshness. They
contain 48 customers with 96 tickets and 8 owner profiles, 22 knowledge
documents with 88 sections, 18 incidents with 144 timeline events, and 64
cross-application memory sources. Their 154 public development cases grade
local business permission, Top-1 retrieval/abstention, diagnostic responsibility,
and memory-governance actions respectively. They are not held-out model
benchmarks. Gold is kept in case records and is not consumed by the executor.
The generated App serializes the same executor and evaluated input.

The native Memory corpus also exposes the added sources while excluding
non-committed, non-consented, retired and revoked material from current atoms.
Input Studio has ten additional project-term candidates with explanatory
reasons. Context inspection shows three scope-bound source excerpts and uses
`token` terminology. Existing original Support, Wix, Enterprise RAG experiment
and Geo application data and historical measurement receipts remain separate.

The stable-input history contains only committed samples, retains each supplied
source timestamp and application, and identifies committed voice input as voice.
Its summary counts are derived from the same records. The Memory walkthrough
opens the new PAW write/registration/recovery topic and its original source.

In the exported customer App, accepted handovers consume shared owner capacity,
advance the customer revision, and retain an operation receipt. A repeated
handover is a readback; a stale displayed proposal is rejected. Undo restores
the owner, capacity and revision together. Memory retirement is persisted with
the collection so replaying a revoked or superseded source cannot resurrect it;
undo restores the collection and retirement state together. These remain local
browser-copy operations, not production transaction or concurrency guarantees.

The repair demonstration executes only its eight built-in faults, initial
virtual workspace and fixed grading checks. Edited checks and arbitrary new
materials are rejected before freeze/replay, rather than being silently ignored.
Restore the built-in inputs to compare again; older reports remain readable.

## Technical articles and full-viewport workspaces

The five detail routes are continuous technical articles covering collaboration,
context, input, frontend evolution and evaluation. The content emphasizes actual
implementation, ownership, failure handling, concrete examples and measured
results for technical readers. Native PAWOS workspaces occupy the complete
viewport outside the article column, with operation and return controls in a
compact overlay. Stable fragment links locate article sections or the full
workspace. Sources and earlier technical records remain expandable.

Input measurements retain two protocols: the 40-prefix model comparison and
the 30-prefix Runtime benchmark. Rule violations use a candidate denominator;
latency uses complete Top-3 generation. These results do not establish human
naturalness or an independent held-out gain. Completion training is shown as
its loss-mask, SFT and frozen-evaluation workflow; unavailable historical
training-report figures are not reused as new claims.

Retrieval's 16-question historical ranking evaluation, the later four-case
answer evaluation, 154 public business-rule cases and eight recovery faults
remain separate sections. The interactive Precision, Recall, RR and nDCG
calculator is an illustrative single-question calculation. It is not an
experiment result. Public world JSON files in `paw-story-demo/public/evidence/`
are byte-identical materializations of the owned source datasets.


## Guided Lab and portable research conversation

The four Lab journeys use the existing public datasets and real local computation. Research loads 200 existing synthetic documents and 16 train questions with source-presence checks. Candidate scores are recomputed with the selected chunking and retrieval configuration. The best measured candidate is limited to these questions; it is not held-out answer-quality evidence.

A separate curated paper-project replay contains 72 historical operations and four saved research responses. Its manifest reports 211 attempted PDFs, 209 readable and two failed. Only filenames, citation excerpts, saved report text and whitelisted aggregate receipts enter the derivative. Local paths, Runtime IDs, credentials and complete PDFs are excluded. Citation destinations are mapped to the included excerpts without changing report wording.

The research App compiles the actual PAW PortableConversation, ComposerShell, ConversationSurface, Markdown renderer, SourceReader and report exporter from this repository. The offline bridge supplies recorded results and rejects unrecorded questions. The other three App exports reuse the existing vertical business frontend with the exact configuration evaluated in the guided Lab. Downloaded HTML and preview are identical. Generated bundles and archives are excluded from the source manifest.

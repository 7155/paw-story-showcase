# PAW 项目介绍网站：本地修改 Handoff

## 1. 这是什么

这是 PAW 项目介绍网站当前线上版本的可编辑源码。它不是 PAW 主项目本身，而是一个用于讲解 PAW 产品愿景与真实 UI 交互的单页 Story Demo。

技术栈：React 19、Next.js/Vinext、TypeScript、Vite、CSS、Lucide Icons。

当前页面只有一个正式路由：`/`。

## 2. 当前产品目标

参考 Tutti · VM 官网的叙事节奏，做一张从上到下连续阅读的单页：

1. 第一章：智能输入法。
2. 第二章：多 Agent 架构。
3. 后续再继续加入 OS 记忆、知识库和沙盒浏览器。

页面不是功能列表，而是用真实 UI 状态回放解释 PAW 为什么存在、用户遇到什么问题、PAW 如何解决。

严禁重新拆成 `/agents` 等独立介绍页面。

## 2C. 从原话提炼出的原始需求

以下需求优先级高于具体页面实现：

1. 网站最终是一张连续的项目介绍单页，不为每项能力单独建立跳转页面。
2. 叙事按章节向下展开：输入法 → 多 Agent → OS 记忆 → 知识库 → 内置沙盒浏览器。
3. 所有演示必须由真实前端组件和预设事件驱动，不使用录屏。
4. 输入法是第一章，因为电脑上的大多数个人意图最终归结于语音和打字。
5. 普通输入不被 AI 打断；完整提交后才出现短联想；主动“生成”后才读取上下文和记忆。
6. 输入法联想框必须跟随输入光标，尺寸紧凑，不能遮蔽文档。
7. RAG 和数据源必须被看见，用户能理解这次补全读取了什么。
8. 多 Agent 章节先解释主从、蜂群、平等专家协作的价值与失败模式，再引出 PAW 的组合方案。
9. PAW 的 Session 内部允许主从；Room 层只保留少量围绕共同目标协作的平等伙伴。
10. 原始需求、任务文档与技能流是整个项目的共同事实和引力；Plan 可以被执行 Agent 质疑和修订。
11. 每个行星代表一条纵向交付轨道，每条轨道自己完成实现、TDD、证据与验收；卫星表示 Session 内的小 Worker。
12. 跨轨道以文档沟通为主，必须限制无限 `@`、无限打回、防御性评审和缺少证据的 P0 声明。
13. 视觉总体参考 Tutti：暖白工作台、大字号、清楚的叙事层级；深色太阳系只作为局部核心演示。
14. 酷炫来自真实状态、轨道关系、局部放大和节奏控制，而不是无意义粒子、过多卡片或很小的仪表盘文字。

## 4. 第一章：智能输入法的叙事要求

核心结论：电脑上的大多数意图最终落到语音和打字，所以输入法是个人 AI 的系统入口。

演示必须遵守以下顺序：

1. 用户正常打字，拼音组合阶段只显示 Rime 候选。
2. 用户提交完整句子后，才在输入光标后方弹出三条短联想。
3. 普通联想只预测下一句，不主动读取远程记忆。
4. 用户点击“生成”后，才读取获准使用的当前文档、最近完整输入、个人记忆与知识库事实。
5. 生成面板逐步显示“读取界面 → 补充近期上下文 → 查找记忆 → 组织回答”。
6. 展示本轮实际使用的数据源和授权边界。
7. 用户确认后把下一段插入文档，并保留可撤销回执。

已有三个文档场景：

- 工作报告。
- 产品需求文档。
- 论文写作。

内容必须像用户真正期待写进文档的下一段，不能使用“这里将展示某某能力”之类没有文档价值的占位文字。

### 输入法 UI 约束

- 输入法候选必须锚定输入光标，不能漂在屏幕中心。
- LLM 联想框保持紧凑，不能遮住大半个文档。
- 拼音候选、短联想、生成中、生成结果是不同状态，不要混成一个大弹窗。
- 动画节奏要快，状态可看清，但不能让用户等待。
- 必须是 React 组件和预设事件回放，不使用录屏或视频。
- 文字必须清晰，并适配桌面和移动端。

## 5. 第二章：多 Agent 的叙事要求

第二章必须直接接在输入法下面，不跳转页面。

### 先引出问题

展示三种常见结构的局限：

1. **主从树**：子 Agent 只能向主 Agent 汇报；计划、上下文和验收都堵在一个入口。
2. **全连接蜂群**：所有 Agent 可以互相 `@`，但消息、等待、重试和状态组合快速失控。
3. **平等专家组**：专业 Agent 可以互补偏见，但没有证据门槛与审核上限时，会陷入防御性否决和无限打回。

### 行业基线

- Anthropic：Orchestrator–Workers。Lead Agent 动态创建专门 Subagent，用于单模型难以覆盖的广度探索，再把结果汇总回主线程。
- OpenAI：Manager / Handoffs。先明确最终答复所有权；Manager 可以保持控制，也可以通过 Handoff 转移所有权。

不要把这两者写成错误方案。它们是有价值的基础模式；PAW 的重点是把不同模式放到不同层级。

### PAW 的组合架构

- **Session 内部**可以使用主从模式：主 Agent 调用小 Worker 完成读取、改写、搜索和局部验证，以节省 token、提升速度并保持主上下文干净。
- **Room 层级**只保留 2–4 个行星级伙伴：它们都围绕同一个用户目标工作，可以质疑 Plan，也可以修订自己的任务文档。
- 每条轨道是纵向交付，不只是“前端 Agent”或“后端 Agent”。它必须同时交付实现、测试、依据、证据和未解决风险。
- 原始需求始终保留。Plan 是可修订假设，不是执行者不可质疑的命令。
- 跨轨道默认通过任务文档与结果回执交流，不把连续互相 `@` 当作主流程。

### 太阳系视觉语义

- 恒星：原始需求、任务文档和技能流，是整个项目的共同引力与事实源。
- 行星：研究、实现、验证、交付四条纵向轨道。
- 卫星：每个 Session 内部的 Worker，用于读取、改写和局部验证。
- 轨道上的流动线：文档更新和结果回执，不是聊天消息。
- `sources.md`、`implementation.md`、`verification.md`、`delivery.md`：各轨道的可核查产物。

治理规则：

1. 文档优先通信。
2. Plan 允许被执行伙伴修订。
3. P0 问题必须带复现步骤、影响范围与失败证据。
4. 审核循环有明确上限，超过阈值必须升级为决策。

最终结论：

> Session 可以是高效的主从系统。Room 必须是一组围绕共同事实工作的伙伴。

## 6. 视觉方向

目标仍然是 Tutti · VM 官网，而不是传统黑色 AI SaaS 页面。

### 页面基调

- 暖白或浅冷灰主画布。
- 大号、粗黑、克制的标题。
- 淡紫、淡蓝、淡绿和暖粉作为解释区块。
- 轻边框、轻阴影、较大的留白。
- 深色只用于太阳系架构演示等需要强对比的核心舞台。

### 不要做

- 不要让整页都是黑色星空。
- 不要堆大量小型控制台、指标标签和看不清的小字。
- 不要使用同质化 SaaS 渐变卡片墙。
- 不要让装饰粒子比产品关系更抢眼。
- 不要为了“酷炫”牺牲内容层级和可读性。

### 动效原则

动效必须解释状态或关系：

- 路径流动表示文档回执。
- 行星高亮表示当前工作的交付轨道。
- 卫星公转表示 Session 内部 Worker。
- 蜂群中的抖动消息表示失控的互相 `@`。
- 用户开启 `prefers-reduced-motion` 后必须停用循环动效。

## 7. 本地运行

环境要求：Node.js `>= 22.13.0`。

```bash
npm install
npm run dev
```

生产构建：

```bash
npm run build
```

完整验证：

```bash
npm test
```

不要提交或回传以下目录：

- `node_modules/`
- `dist/`
- `.next/`
- `.vinext/`
- `.wrangler/`
- `.git/`

## 8. 建议的本地修改顺序

1. 先只调整 `MultiAgentChapter` 的信息密度和太阳系构图。
2. 再统一输入法与第二章的标题、留白、圆角和颜色。
3. 最后调整动效速度与移动端布局。
4. 每次修改后先运行 `npm run build`。

不要一开始重写全部技术栈，也不要把真实 UI 回放改成图片或视频。

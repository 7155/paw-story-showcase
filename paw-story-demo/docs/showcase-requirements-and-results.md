# PAW 展示页需求与结果

## User Requirement Ledger

### SHOW-001｜公开、独立的功能展示项目｜current · P0

- 当前要求：在新项目中用真实 PAW 前端展示能力，数据使用公开合成示例；最终公开并推送。
- 用户可见验收：访问一个公开页面即可操作三个主章节，不依赖用户本机 PAW 数据或服务。
- 必须保留：真实前端的视觉、组件和交互；合成数据标识；新项目自身可构建。
- 禁止：复制真实 transcript、个人输入、记忆数据库、凭据或私有 Runtime 状态；把示例事件称为生产运行。
- 来源：当前 oshow Goal 会话，2026-08-28。
- 用户原话：`前端加上示例数据放到新项目可以吗，只是用来做每个功能的实际展示`；`新建，public`；`你push才行`。

### SHOW-002｜第一章：智能输入与语音文字定稿｜current · P0

- 当前要求：第一页使用本项目真实输入法前端，同时展示语音转文字以及保守的文字纠错/写回过程；展示站在候选出现后自动模拟一次“点击生成”，避免被动观看者错过结果。
- 用户可见验收：可在“智能输入法”和“语音转文字”之间切换，看到输入、上下文补充、候选或转写、定稿、写回的连续状态；候选停留约 2 秒后按钮出现已点击反馈并自动进入流式生成，最终结果停留等待采纳或拒绝。
- 必须保留：自动点击只属于公开展示回放并在界面明示；真实 PAW 产品仍由用户触发生成，最终写入仍由用户采纳或拒绝；语音内容只作为合成示例。
- 禁止：将其改写为语音播报，或声称保存了真实音频。
- 来源：当前 oshow Goal 会话，2026-08-28。
- 用户原话：`AI 不必等你 打开聊天框这个部分再吧本项目的语音转文字和和输出改正加入，也是用本项目前端`；修订：`生成按钮自动点击，不然用户不一定看得到生成结果`。

### SHOW-003｜第二章：原始输入到时间线、词库与项目上下文｜current · P0

- 当前要求：用实习场景说明每天数百/上千条完整输入如何连同应用、文档上下文被整理为时间线、词库、项目文件关系与可治理记忆。
- 用户可见验收：点击时间线条目可看到原始句子、发生位置与整理结果；所有数量均明确是示例。
- 必须保留：原始句子和上下文的可回溯关系；词库、项目文件、个人记忆不是同一个存储范围。
- 禁止：使用真实个人输入，或把输入自动等同于永久记忆。
- 来源：当前 oshow Goal 会话，2026-08-28。
- 用户原话：`比如说每天他整理几百条上千条的输入，然后形成时间时间线。还有词库，还有项目的这些文件作为上下文。`。

### SHOW-004｜Project Docs、User Memory、Knowledge Mount 三类治理边界｜current · P0

- 当前要求：项目文档保存项目需求和工作事实；用户记忆独立处理并受显式授权；知识库按论文、企业等场景外挂。
- 用户可见验收：三种来源可分别选择，并各自显示调用条件、召回时机和权威载体。
- 必须保留：User Memory 默认不越权读取；仅在用户显式开启或工具获权时参与；每个 compact/大对话周期至多主动召回一次。Knowledge Mount 不默认进入所有对话。
- 禁止：静默合并三个范围，或让项目文件成为个人偏好的第二副本。
- 来源：当前 oshow Goal 会话，2026-08-28。
- 用户原话：`用户记忆就这个是输入法，针对他的用用户偏好。这个的话就不属于项目，所以就是单独处理的。为了隐私，所以它只能有权限的时候，工具有权限的时候才能调用，或者用户显示开启这个功能`；`每一次 compact 就是每一个大的对话周期，它就会召回一次`；`还有个是知识库，这个是用作不同的场景，比如说你 agent 用作论文写作或者企业知识库管理，这些时候它就会外挂。`。

### SHOW-005｜RAG 演进与 Trace/Eval｜current · P0

- 当前要求：展示 Embedding、Hybrid、Rerank、Agentic RAG，并让 Trace 解释召回是否正确、准确率/召回率、引用和后续自动优化。
- 用户可见验收：同一问题可切换检索策略；同一 Trace 中真实标签计算的指标与 AI Judge 估计分栏；自动优化明确显示“正在添加”。
- 必须保留：数据集版本、查询、范围、候选、重排、证据和 Judge 的可追溯边界。
- 禁止：把页面里的合成指标冒充生产测量，或把 AI 估计冒充人工标签。
- 来源：当前 oshow Goal 会话，2026-08-28。
- 用户原话：`有 传统的 Embedding 向量召回，呃，这些，和，各种增强， Agent 的 rag。`；`展示那个 trace 就是它是怎么检查这些，召回对不对，还有准确率。嗯，准确率、召回率、也可以指标，还有自动优化这些。目前正在添加这些功能，正正在添添加。`；`还有完成记忆的全部整理，找找rag数据集之类的`。

### SHOW-006｜第三章：Goal 太阳系变形为真实 PAWOS 窗口｜current · P0

- 当前要求：太阳代表原始文档 Goal，行星代表纵向 WorkItem；先旋转展示关系，再渐变为真实 PAWOS 桌面和多个窗口。
- 用户可见验收：可重播关系视图到执行窗口的变形，也可直接切到执行窗口；最终窗口由实际 PAWOS 组件渲染。
- 必须保留：真实 UI 与合成事件的标签边界；窗口不是重新画出的网页仿制品。
- 禁止：以截图、视频或静态假窗口替代实际可交互 DOM。
- 来源：当前 oshow Goal 会话，2026-08-28。
- 用户原话：`比如他一个太阳，就是那个文档目标，然后多行星 是各自纵向分配的任务。`；`旋转一会，然后就可以 把那些行星和这些都变成窗口。渐变整窗口`；`03 · 进入真实窗口态要真实的os界面啊。真实前端，真实os界面动画弹出这么多的窗口`。

### SHOW-007｜有序 Room 执行、WorkPatch 与独立 Reviewer｜current · P0

- 当前要求：Facilitator 先分派实施伙伴；实施伙伴流式完成并提交 WorkPatch，不自行做最终测试；全部 WorkPatch 到齐后才启动独立 Reviewer，Reviewer 按原始需求和代码检查且 P0 为零后最终提交。
- 用户可见验收：只出现一条有序活动流；Reviewer 在 3/3 WorkPatch 前保持 gated；最终回执显示测试、需求复核与 P0 结果。
- 必须保留：实施与最终测试的职责分离；Reviewer 是 Facilitator 决定是否分派的独立工作批次。
- 禁止：多路消息交错刷屏，或在补丁未齐时提前启动 Reviewer。
- 来源：当前 oshow Goal 会话，2026-08-28。
- 用户原话：`测试是最后交给一个伙伴测试的`；`是否安排测试是由Facilitator决定`；`分派干活的人不用测试，有专人测试`；`必须要展示运行过程，就是流式输出，分派任务各自完成，测试提交`；`测试者要忠于需求和代码无p0`。

### SHOW-008｜额外能力不删除，只收进跳转入口｜current · P1

- 当前要求：知识图谱、沙盒 Browser 等既有页面继续保留，但不抢占三个主章节，统一放在额外功能入口后。
- 用户可见验收：主叙事保持三章；点击“更多功能”仍能进入既有演示。
- 禁止：删除既有能力页面，或把它们重新塞进主滚动叙事。
- 来源：当前 oshow Goal 会话，2026-08-28。
- 用户原话：`那些多余页面不是删除，而是放到一个跳转按钮`。

### SHOW-009｜真实 OS 展示采用常规网页画幅｜current · P0

- 当前要求：真实 PAWOS 窗口态不能成为过长的横向条带；桌面网页按 16:9 展示，窄屏按 4:3 展示。
- 用户可见验收：桌面宽屏中的嵌入舞台宽高比为 16:9；820px 及以下视口中的舞台宽高比为 4:3，内容仍被舞台边界裁切。
- 必须保留：第三章既有协同关系、变形和实际 PAWOS 窗口流程。
- 禁止：为了适配比例删掉协同内容，或把真实窗口换回截图。
- 来源：当前 oshow Goal 会话，2026-08-28。
- 用户原话：`你这个比例太长了，而且那展示合作拿好的啊`；`os16:9`；`或者4:3`；`因为是网页`。

### SHOW-010｜三章风格统一且文字足够醒目｜current · P0

- 当前要求：三个主章节采用同一套有气势的产品叙事层级；第二章首先回答“一天上千次输入，最后留下什么”，不能再是密集的小字号仪表盘。
- 用户可见验收：第二章采用与第一、三章一致的大标题、宽留白和大卡片；Project Docs、User Memory 与 Knowledge/RAG 分为三个明确切换场景；重要正文在桌面和手机上均可直接阅读。
- 必须保留：记忆形成、治理边界、RAG 演进与 Trace/Eval 信息；可缩小辅助标签，但不能让关键含义依赖 6–9px 小字。
- 禁止：通过删除关键指标来制造简洁，或让所有信息同时堆叠在一个超长面板中。
- 来源：当前 oshow Goal 会话，2026-08-28。
- 用户原话：`一天上千次输入，最后留下什么？就是每个页面风格统一，字要大一点。字很多小的根本就找不到，而且很丑，这个页面很小气。`。

### SHOW-011｜第二章是三个真实可切换页面｜current · P0

- 当前要求：第二章按“项目文档、用户记忆、知识库”三个页面组织，不再用一个一直展开的治理面板加一个黑色 RAG 面板。
- 用户可见验收：三个标签都可点击；同一时间只显示对应页面；项目文档显示结构与正文，记忆显示输入时间线，知识库用浅色关系图解释 Embedding、Hybrid、Rerank 与 Agentic RAG。
- 必须保留：三个范围各自的调用条件、召回时机和权威载体；知识库仍显示真实指标与 AI 估计的边界。
- 禁止：纯黑知识库大面板；只有外观、不能点击的假切换；用卡片堆叠替代关系图。
- 来源：当前 oshow Goal 会话，2026-08-28。
- 用户原话：`rag为什么是用纯黑的？还有图，我们是用那个图配方来说的。而且是三个页面，一个是文档，文档结构就直接把那个那些OpenAI那个搬进来就行。第二个就是，嗯，记忆，第三个就是知识库，代表这三个页面做成切换的。`；`动不了`。

### SHOW-012｜Project Docs 是 Agent 的项目引力场｜current · P0

- 当前要求：Project Docs 不是普通文件库，而是以本展示项目的真实 Goal 为中心，令仓库中真实存在的范围、需求、数据、Eval 和来源文档共同约束 Agent 执行轨道的“引力场”。
- 用户可见验收：页面明确写出“不是普通 docs”；左侧直接列出 `README.md`、`paw-story-demo/README.md`、展示需求台账、`SHOWCASE_DATA.md`、RAG/Memory Eval 数据集说明和 `UPSTREAM.json`，中间是所选真实文档的路径、原文摘录、清洗回执与正文结构，右侧是当前文档目录；小型 Goal 锚点只解释这些文档为何共同约束执行，不再绘制抽象行星或轨道图。
- 清洗边界：真实文件只投影与公开展示直接相关的职责、规则和证明边界；不得显示本机路径、账号、会话标识、完整 transcript、个人数据、凭据、私有 Runtime 状态或尚未验收的完成声明。页面必须显式标注“真实文件 · 已清洗”，不能再以虚构项目文档冒充本项目事实。
- 结构参考：[OpenAI《工程技术：在智能体优先的世界中利用 Codex》](https://openai.com/zh-Hans-CN/index/harness-engineering/) 中“代码仓库作为记录系统”“给 Agent 地图而不是千页说明书”“渐进式披露”的组织原则；文档来源是真实仓库，正文为清洗后的公开投影，只有业务场景与 Runtime 状态继续使用合成示例。
- 禁止：把参考文章正文复制为本站内容；用虚构文件名、装饰性关系图或抽象轨道替代实际文档阅读；把清洗后的公开摘录冒充完整源文件。
- 来源：当前 oshow Goal 会话，2026-08-28。
- 用户原话：`Project Docs就作为引力场https://openai.com/zh-Hans-CN/index/harness-engineering/`；`得表明这不是普通的docs`；修订：`Project Context Gravity用本项目的真实文档，不过要清洗`；再次纠偏：`这个换成实际文档呀`；`因为你画的这个莫名其妙的`。

### SHOW-013｜第二章动效与特效服务同一主题｜current · P1

- 当前要求：第二章加入动效和特效，但三页必须维持同一套浅色纸张、绿色上下文流与大字号主题。

- 必须保留：`prefers-reduced-motion` 下移除旋转、位移和脉冲，只保留轻量透明度反馈。
- 禁止：移动正文、持续闪烁、未受控粒子或为特效重新引入黑色主题。
- 来源：当前 oshow Goal 会话，2026-08-28。
- 用户原话：`第二页加点动效和特效，主题统一`。
